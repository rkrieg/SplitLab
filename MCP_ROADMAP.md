# SplitLab MCP Server — Phased Roadmap

Goal: match Unbounce's MCP feature set (connect Claude/ChatGPT via OAuth, build/edit/publish pages, manage A/B tests, track results — see their docs) using SplitLab's existing backend logic, without reimplementing our own AI-editing pipeline. Claude writes the content; SplitLab exposes structured tools.

Legend: `[ ]` not started · `[~]` needs backend work first (no existing SplitLab route/schema to wrap) · `[✓]` reuses an existing, already-hardened pattern

## Phase 1 — Connect, describe, build, preview, publish
*(Unbounce: "Getting Connected" + "Your first page" + core "Build and edit pages")*

- [x] `list_clients` / `list_workspaces` — `list_clients` already returns each client's `workspaces` nested (id/name/slug/status), which is everything a `list_workspaces` tool would separately expose — no second tool built, would've been a pure duplicate.
- [x] `list_pages` — not in the original checklist but required for the flow to actually work (Claude needs a way to enumerate pages in a workspace before it can `get_page`/`update_page` one). Wraps the same query as `GET /api/workspaces/[id]/pages`, now shared via `listWorkspacePages()` in `src/lib/services/pages.ts`.
- [x] `create_page` — Claude writes HTML, tool stores it as a **Draft**, unpublished, in the chosen workspace. Gated on the owner's plan having `aiPages` (same gate `generate`/`build`/`follow-up`/`upload-image` already enforce — this is the same category of feature, Claude authoring content, so it inherits the same paywall) and on `workspace role !== viewer` + OAuth write scope.
- [x] `update_page` — the tool schema has no `draft` parameter at all; the handler always passes `draft: true` to `updatePageDraftOrLive`, so there is no code path that can write a live variant's served HTML. Same `aiPages` + role + scope gates as `create_page`.
- [x] `get_page` — full page row (live + draft HTML, linked-variant info if the page backs a test) plus `preview_url`/`draft_preview_url`, both `${APP_URL}/api/pages/[id]/preview` — a **SplitLab-hosted URL**, resolved by the human's existing logged-in browser session, matching how the dashboard's own preview link already works.
- [x] `publish_page` / `unpublish_page`
- [x] `delete_page` — wraps the existing **soft-delete** (`deleted_at`); added `softDeletePage()` and made sure the tool calls that, not the *other*, still-present hard-delete `DELETE /api/pages/[id]` handler (found both exist in the codebase — same soft-delete-vs-hard-delete split matters here as it did for tests/variants).
- [x] Images/assets upload (base64-paste case) — the actual "user pastes an image into Claude" flow is now handled: `createPage()` and `updatePageDraftOrLive()` in `src/lib/services/pages.ts` run any `html_content` they're given through the already-hardened `inlineDataUrisToStorage()` (`src/lib/storage.ts`, previously only wired into 5 other HTML-accepting write paths) before storing it — Claude can embed a pasted image as a base64 `data:` URI directly in the HTML it writes via `create_page`/`update_page`, and it gets decoded, magic-byte-validated, uploaded to the `ai-pages-images` bucket, and spliced back in as a real public URL, no new tool needed. `createPage()` now generates its own `pageId` up front (`crypto.randomUUID()`) since the Storage upload path requires one before insert. No new SSRF surface: this only decodes bytes the caller already handed over inline, it never fetches a URL server-side.
  - `[~]` Image upload **by URL** (Claude/user supplies a link instead of pasting bytes) remains deferred: a backend that fetches arbitrary caller-supplied URLs is a textbook SSRF surface (could be pointed at internal services/cloud metadata endpoints) — needs an allowlist/egress-restriction design pass before it's wired up, not a quick wrap.

**Bug found and fixed while verifying this phase:** `publishPage()` (written in Phase 0) assumed `html_url` is always set — true for every *existing* page-creation path, all of which upload to Storage immediately. `create_page` is the first path that ever stores `html_content` only (matching plain `POST /api/pages`'s own convention), and publishing such a page crashed. Fixed by falling back to a fresh `pages/{id}.html` Storage path when `html_url` is absent — a latent gap in existing code that MCP's traffic pattern was first to hit, not a new behavior for any pre-existing caller.

**Verify (done):** `list_clients` → `create_page` (real prompt) → confirmed Draft row in DB → `get_page` → `update_page` → `publish_page` → confirmed live URL resolves (200) with edited content → `unpublish_page` → confirmed URL now 404s → `delete_page` → confirmed excluded from `list_pages`. Also checked: missing-field rejection is graceful (not a crash), nonexistent `page_id` returns a clean "Not found." Not yet checked live (no viewer/non-aiPages-plan test account available this session): a viewer-role token's write attempt, and the `aiPages` plan-gate rejection on a non-admin free-plan workspace — both paths were code-reviewed against the identical, already-proven pattern used by `generate`/`build`/`follow-up`/`upload-image`, but should get one real run before this ships broadly.

## Phase 2 — Variants & A/B tests
*(Unbounce: "Create variants and run A/B tests")*

**Found missing while live-testing Phase 1** (real Claude session tried this exact flow and hit a dead end — see roadmap history): Phase 1 lets Claude create a standalone AI page and edit its content, but there was no tool to then attach that page to a test, or to push a linked page's draft live. That's a gap in the *page* lifecycle, not just a Phase 2 "new variant management feature" — without these, `create_page`/`update_page` dead-end at "draft that only a human can finish wiring up." Adding here since they operate on `test_variants`, same as the rest of this phase:

- [x] `list_tests` / `get_test` — **discovery gap, closed**: `listWorkspaceTests`/`getTestDetail` in `src/lib/services/tests.ts`, wrapping `resolveWorkspaceRole`/`resolveTestWorkspaceRole` (viewer-read-allowed, non-member-403, same as the dashboard). Response includes every variant's `id`/`traffic_weight`/`is_control`/`archived_at`/`page_id` and every goal's `id`, so `update_test_weights`/`update_test_goals` below can echo ids back without regenerating.
- [x] `save_page_as_variant` — `attachPageAsVariant()` in `src/lib/services/pages.ts`, extracted verbatim from `/api/pages/[id]/save-as-variant`. Enforces the page-backs-one-variant invariant via `getLinkedVariant` and re-checks the test's plan variant-count limit.
- [x] `save_page_as_new` — `forkPageAsNewVariant()`, extracted verbatim from `/api/pages/[id]/save-as-new`. Forks draft-or-live HTML into a new page + 0%-weight variant on the same test, clears the original's draft afterward.
- [x] `replace_variant` — `replaceVariantLive()`, extracted verbatim from `/api/pages/[id]/replace-variant`. Tool description is flagged DANGER — promotes a linked page's draft onto live immediately, no separate confirmation step at the transport level.
- [x] `duplicate_variant` — wraps the already-built `duplicateVariant()` service function (0% weight, `duplicated_from_id`, plan limit re-checked, skips goals/personalization).
- [x] `create_variant` — `createVariant()` in `tests.ts`, extracted verbatim from `POST /api/tests/[id]/variants` (fresh/blank variant, distinct from duplicate; equalizes all weights after insert).
- [x] `duplicate_test` — wraps the already-built `duplicateTest()` service function (forces new test to `draft`).
- [x] `update_test_weights` — wraps `updateTest({ weights })`. Tool handler additionally rejects any call whose id set doesn't exactly match the test's full active (non-archived) variant set — a partial/single-variant patch is rejected before `updateTest` even runs, not just relying on its sum-to-100 check.
- [x] `archive_variant` / `unarchive_variant` — wraps `updateTest({ archive_variant_id })`/`{ unarchive_variant_id }` (guards: can't archive last active variant, always calls `redistributeActiveWeights()`).
- [x] `rename_variant` — wraps `updateTest({ variant_updates: [{ id, name }] })`.
- [x] `promote_to_champion` — **new logic, verified needed**: no existing route ever swapped `is_control` after creation (grepped — only ever set once, at creation time). Added `promoteToChampion()` in `tests.ts`: unsets `is_control` on every variant in the test, sets it on the target, refuses to promote an archived variant. Tool description notes this is a label change only — does not itself move traffic.
- [ ] `[~]` "Edit every variant at once" (apply the same change across all of a page's variants in one request) — still deferred; no existing batch endpoint, needs new service-layer logic (loop `updatePageDraftOrLive` across all variant pages of a test inside one transaction/guard), not just a wrapper.
- [x] `update_test_goals` — wraps `updateTest({ goals })` (full-replace-by-diff, preserves existing UUIDs for goals Claude re-lists so `events.goal_id` history doesn't orphan — tool description explicitly warns against inventing ids for existing goals).

**Verify (not yet run — needs a connected Claude session against a seeded dev workspace):** `npm run build` passes (done). Still to do live: `list_tests`/`get_test` → `create_variant` → `duplicate_variant`, confirm 0% weight → `update_test_weights` with a partial id set, confirm rejection, then full set, confirm applied → `archive_variant` down to the last active one, confirm rejection → `rename_variant` → `promote_to_champion`, confirm previous champion's flag cleared → `update_test_goals`, confirm UUIDs unchanged in DB → `save_page_as_variant` on a fresh `create_page` draft → `save_page_as_new` on that same now-linked page → `replace_variant`, confirm live HTML changes only then. Also: a viewer-role token rejected on every write tool above, reads still scoped correctly.

## Phase 3 — URL, domain assignment, SEO
*(Unbounce: "Publish and set up the URL")*

- [x] `set_page_slug` — `setPageSlug()` in `src/lib/services/pages.ts`, wired as the `set_page_slug` MCP tool. Takes effect immediately, not draft-gated (updates `published_url` too if already published; tool handler calls `revalidatePath` on both the old and new `/pages/[slug]` paths, matching unpublish/delete's existing convention). Found and fixed a latent gap while building this: `pages.slug` has **no DB-level UNIQUE constraint** (checked every migration — only `clients.slug`/`workspaces.slug` are unique), and `pages/[slug]/route.ts` resolves published pages by a bare `.eq('slug', …)` lookup, so two pages sharing a slug would silently break whichever one that query returns. `setPageSlug()` now enforces uniqueness at the application level (same pattern as `updateTest`'s workspace-scoped `url_path` collision check) — this closes a pre-existing gap, not something introduced by exposing it over MCP.
- [ ] `[~]` `assign_domain` — **investigated, does not map onto existing SplitLab architecture**: custom-domain routing is `domains.domain` (host) → **workspace** → whichever **active test**'s `url_path` matches the request (`src/app/api/serve/route.ts`); there is no `domain_id` column on `pages`, and standalone pages (the kind `create_page`/`publish_page` produce) only ever serve from `${APP_URL}/pages/{slug}` — never from a custom domain, published or not. "Move a page to a domain" isn't a data model that exists to wrap; building it for real would mean either (a) inventing a page→domain link that nothing else in the app understands, or (b) redefining it as "wire this page into a test on that domain's workspace," which is really `save_page_as_variant` (Phase 2, already built) + the test's own `url_path`, not a new tool. Left unbuilt — flag for a product conversation if per-page custom-domain hosting is actually wanted, since it'd be new schema + serve-route logic either way.
- [ ] `[~]` SEO/OG fields (page title, meta description, favicon, Open Graph tags) — **verified**: grepped every migration and `src/types/index.ts` for `favicon`/`meta_description`/`og_image`/`meta_title`/`seo` — none exist on `pages`. New schema work, not a wrapper.
- [ ] `[~]` Redirects (old URL → new page) — **verified**: no redirect table exists anywhere in `supabase/migrations/`. New schema + serve-route logic, its own mini-project if wanted.
- [ ] `[~]` Page groups (organizing pages) — **verified**: no equivalent surfaced in schema or routes; SplitLab's client → workspace hierarchy likely already covers this need — worth confirming with the team whether page groups add anything beyond existing workspace scoping before building it.
- [x] `list_domains` / `add_domain` / `verify_domain` / `delete_domain` — **built, distinct from `assign_domain` above**: domain management itself (add to workspace, get Vercel DNS records, verify, delete) is a real, existing, workspace-scoped feature (`src/app/api/workspaces/[id]/domains/route.ts`, Vercel API integration) that maps cleanly onto existing logic — unlike `assign_domain`, which has no data model to wrap. Extracted into `src/lib/services/domains.ts` (`listDomains`/`addDomain`/`verifyDomain`/`deleteDomain`), same pattern as `pages.ts`/`tests.ts`; the HTTP route now calls these too. `add_domain` keeps the owner-plan domain-limit check (via `resolveOwnerPlan`, same helper `requireAiPagesPlan` already uses). `verify_domain`'s tool description explicitly calls out Vercel's 50/hr project-wide verification quota so Claude doesn't loop it. `delete_domain` requires `confirm: true`, same pattern as `delete_test` — Vercel removal + row delete is not undoable through this tool. `update_domain` (swap the domain string in place) is deliberately NOT exposed — it removes+re-adds in Vercel and resets verification, the riskiest of the four operations, and stays dashboard-only for now.

**Verify (not yet run live):** `npm run build` passes (done). Still to do: `set_page_slug` on an unpublished page → confirm no live-URL side effect; on a published page → confirm `published_url` and the actual served `/pages/[slug]` both move to the new slug and the old slug 404s; attempt a slug already taken by another page → confirm 409 rejection, not a silent overwrite. For domains: `add_domain` on a free-plan workspace → confirm `limitError` rejection; `add_domain` → confirm returned `vercel_verification` records match what the dashboard's "Add Domain" modal shows for the same domain; `verify_domain` before DNS is configured → confirm `pending_verification`/`misconfigured` status, then after configuring → confirm `verified: true`; `delete_domain` without `confirm` → confirm rejection; a viewer-role token on all four → confirm read allowed, writes rejected.

## Phase 5 — Distribution surfaces (beyond claude.ai/Desktop connectors)
*(Unbounce: their docs list five separate install paths — Claude Desktop, Claude web, Claude Code CLI, ChatGPT Desktop, Codex CLI — plus an explicit "not supported yet" for ChatGPT web)*

**What we have today**: everything built in Phases 0–4 is reachable exactly one way — a user opens claude.ai or Claude Desktop's Connectors settings, pastes the `/api/mcp` URL (discoverable via `/.well-known/oauth-authorization-server`, built in Phase 0), and completes the OAuth consent flow. This is a real, working, spec-legal MCP connector. It is NOT, however, the only install surface MCP clients support — it's specifically the "custom connector by URL" flow, which only claude.ai and Claude Desktop expose as a user-facing option.

**Why the other surfaces don't just work already**: Claude Code CLI, ChatGPT Desktop, and Codex CLI don't have a "paste a connector URL" screen at all. Each of them installs MCP integrations through a **plugin marketplace** model instead — a public, well-known Git repository (Unbounce's is `unbounce/agent-plugins`) containing a plugin manifest that declares where the MCP server lives (and optionally bundles Skills — packaged prompts/slash-commands like their `/unbounce-mcp:` namespace). The client tooling (`claude plugin marketplace add …`, `codex plugin marketplace add …`) knows how to fetch and parse that manifest; it has no equivalent notion of "just point me at an arbitrary OAuth-discoverable URL" the way claude.ai's Connectors UI does. So this is a **packaging/distribution gap, not a missing-feature gap** — the same `/api/mcp` + OAuth endpoints built in Phase 0 would be what the manifest points at; nothing in the tool surface (Phases 1–4) needs to change to support this.

- `[ ]` Publish a public plugin-marketplace repo (e.g. `splitlab/agent-plugins`, mirroring Unbounce's naming convention) containing a Claude plugin manifest that references the existing `/api/mcp` server + OAuth discovery endpoint — this is the single blocker for Claude Code CLI support (`claude plugin marketplace add splitlab/agent-plugins` → `claude plugin install splitlab-mcp@splitlab`).
- `[ ]` `[~]` Decide whether to bundle Skills (packaged instructions surfaced as `/splitlab-mcp:...` slash commands) alongside the raw MCP tools in that same manifest, the way Unbounce does — needs a product decision on what a "skill" would actually help with here (e.g. a guided "set up an A/B test" flow) versus just exposing the tools directly; not required for the marketplace repo to work, just parity-plus.
- `[ ]` Confirm the same manifest/repo also satisfies ChatGPT Desktop's marketplace flow (`Add a marketplace` → same source string) and Codex CLI's (`codex plugin marketplace add …`) — Unbounce uses one repo for all three, so this is likely one artifact, not three, but needs verifying against each client's actual manifest schema (not yet researched — Claude's plugin manifest format, and whether ChatGPT Desktop's "marketplace" concept is schema-compatible or a separate format, is still unknown).
- **ChatGPT web — confirmed not attemptable, matches Unbounce exactly**: the ChatGPT web app only installs from OpenAI's official Plugin Directory and has no "add a marketplace from a repo" option at all. Unbounce's own doc calls this out as "not supported yet" pending their own Plugin Directory listing — there's no workaround on our side either; this is an OpenAI platform limitation, not something a plugin repo can route around.
- **claude.ai / Claude Desktop — already fully solved, listed here only for contrast**: the custom-connector-by-URL flow built in Phase 0 already covers both of these (they share one install, per Claude's own docs — connecting on either surface connects both, since plugins/connectors are tied to the Claude account, not the client). No new work needed for these two.

**Reasoning for scoping this as its own phase rather than folding it into Phase 0**: Phases 0–4 are entirely about *what the MCP server can do* once a client is connected — auth model, tool coverage, permission parity. This phase is entirely about *how a client discovers and installs* the server in the first place, which is a separate concern with its own artifacts (a public repo, a manifest file) that don't touch `src/app/api/mcp/route.ts` or any service-layer code at all. Bundling it into Phase 0 would have implied it blocks tool-building work, which it doesn't — the tool surface is already complete and usable today via the one connector path that exists.

## Explicitly out of scope / not attempted for parity

- **Smart Traffic** (Unbounce's AI-driven automatic-routing-to-best-variant) — SplitLab has chi-square significance stats (`src/lib/stats.ts`) but no auto-reallocation engine. This is a real feature build, not an MCP wrapper — separate decision, not part of this roadmap.
- **Popups / sticky bars, payments** — no SplitLab equivalent exists at all (Unbounce also keeps these out of its assistant).
- **Permanent asset deletion** — kept in-app only, same exclusion Unbounce makes. (Domain creation/verification/deletion is now exposed — see Phase 3.)
- **SplitLab's own AI generate/build/follow-up pipeline** (`src/app/api/pages/[id]/follow-up/route.ts`) — not wrapped, not reimplemented. This is the fragile system we're moving away from; Claude authors content directly via `create_page`/`update_page`.

## Behavioral parity checklist (matches Unbounce's "How It Works Day to Day")

- [ ] Content/variant/traffic changes stage as drafts by default — publish is explicit (URL/slug is the one exception, takes effect immediately)
- [ ] MCP-created pages remain **editable in the SplitLab dashboard too** (confirmed decision — no Unbounce-style assistant-only lock-in)
- [ ] Delete = reversible (soft-delete, already how `pages`/`tests` deletion works — no new work needed)
- [ ] Claude works from page content/schema, not a rendered screenshot — preview tool is how a human actually sees it
- [ ] The assistant acts as the connected user — same role, same permissions, enforced via existing `workspace-auth.ts`, not a new model
